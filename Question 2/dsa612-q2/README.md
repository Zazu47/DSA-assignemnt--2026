--- Rental Accommodation System — gRPC (Question 2)

A distributed rental/booking platform built with the Ballerina programming
language and gRPC, for the Ministry of Tourism. Hosts manage property
listings; Guests search, book, and Hosts confirm bookings.

--- Project structure

This solution is split into two independent Ballerina projects,
communicating only over the network (as a real distributed system would):

```
rental_system/      <- the gRPC SERVER
  proto/
    rental.proto     <- the service contract
  modules/rental/     <- generated from rental.proto (bal grpc)
  server.bal          <- service implementation (all 8 RPCs)

rental_client/       <- the gRPC CLIENT
  proto/
    rental.proto     <- same contract, copied here
  modules/rental/     <- generated from rental.proto (bal grpc)
  main.bal             <- interactive menu-driven client
```

--- How to run

**1. Start the server** (in `rental_system/`):
```
bal run
```
Leave this running — it listens on `https://localhost:9090` (TLS-secured;
see Security section for certificate setup).

**2. Run the client** (in a separate terminal, inside `rental_client/`):
```
bal run
```
This launches an interactive menu. Choose an option by number, follow the
prompts, and press Enter to return to the menu after each result.

--- Typical usage flow

1. **Sign up** — choose `6. Create users`, create at least one Host and one
   Guest. Copy each printed `user_id`.
2. **Log in** — choose `9. Log in as user`, paste in the Host's `user_id`.
3. **List a property** — choose `1. Add property` and fill in the details.
4. **Browse** — choose `5. List available properties` to see it.
5. **Book** — log in as the Guest (`9`), then `7. Book property`, using the
   property id from step 3.
6. **Confirm** — log in as the Host again (`9`), then `8. Confirm booking`,
   using the `request_id` printed in step 5. This calculates the total cost
   and finalizes the booking.

## The 8 RPCs

| RPC | Type | Who can call it |
|---|---|---|
| `add_property` | unary | Host (must own the listing) |
| `update_property` | unary | Host (must own the property) |
| `remove_property` | unary | Host (must own the property) |
| `search_property` | unary | Anyone |
| `list_available_properties` | server streaming | Anyone |
| `create_users` | client streaming | Anyone (this is how you get an identity) |
| `book_property` | unary | Guest |
| `confirm_booking` | unary | Host (must own the property) |

## Key design decisions

- **PropertyStatus and UserRole are enums**, not strings — both have a
  fixed, known set of values, so an enum gives compile-time safety and a
  smaller wire format. Enum value `0` is always `UNSPECIFIED`/
  `ROLE_UNSPECIFIED` (never a real state), so a field that's accidentally
  left unset is obviously wrong rather than silently valid.
- **`property_type` is a plain string**, since the set of possible property
  types isn't fixed or known in advance.
- **Separate "New...Request" and full message types** (`NewPropertyRequest`
  vs `Property`, `NewUserRequest` vs `User`) — ids are generated by the
  server, so the creation request simply has no id field to tamper with.
- **`UpdatePropertyRequest` uses `optional` fields** so a Host can update
  just the price without needing to resend every other field. The server
  only touches fields that were actually provided.
- **Two-tier booking**: `book_property` performs basic validation and an
  early clash check against confirmed bookings (for fast Guest feedback),
  and adds the request to a temporary in-memory "cart"
  (`pendingBookings`). `confirm_booking` — called by the Host — repeats the
  authoritative overlap check (since more bookings could have been
  confirmed in between) before finalizing.
- **Real authentication via gRPC metadata**: a user's server-generated
  `user_id` (from `create_users`) is their credential. Every protected RPC
  reads a `user_id` header (via the generated `...Context` request/client
  types), looks up who that actually is in the server's own `users` map,
  and checks their role — rather than trusting any `host_id`/`guest_id`
  field written in the request body. This closes a real gap: without it,
  anyone could claim to be any Host or Guest by simply typing a different
  id into a request.
- **`list_available_properties` uses direct-return streaming**
  (`returns stream<Property, error?>|error`) rather than the
  caller-based pattern. This was a deliberate choice after finding a
  documented bug in the Ballerina gRPC compiler's validation of
  caller-parameter server-streaming functions — direct-return is an
  equally valid, officially documented pattern, and is the better fit
  here since nothing about listing properties is genuinely asynchronous.
- **Booking cart expiry**: a `book_property` request that's never
  confirmed doesn't stay in the cart forever — `cleanupExpiredBookings()`
  removes any pending request older than 15 minutes, checked lazily
  whenever `book_property` or `confirm_booking` runs (no background task
  needed).

## Security

- **Authentication**: a user's server-generated `user_id` (from `create_users`)
  acts as their credential. Protected operations send it as a `user_id`
  gRPC metadata header; the server looks up the real user and enforces
  role (HOST/GUEST) and ownership before acting.
- **Transport encryption (TLS)**: the server presents a self-signed
  certificate (`server.p12`, generated via `keytool`) and listens over
  TLS; the client connects via `https://` and trusts the server's public
  certificate (`server-public.crt`). This means the `user_id` credential
  and all request/response data travel encrypted, not in plaintext.
  To regenerate the certificate (e.g. for a different machine or a fresh
  clone of the repo):
  ```
  keytool -genkeypair -alias rental -keyalg RSA -keysize 2048 -validity 3650 \
    -keystore server.p12 -storetype PKCS12 -storepass ballerina \
    -dname "CN=localhost, OU=Rental, O=NUST, L=Windhoek, ST=Khomas, C=NA"
  keytool -exportcert -alias rental -keystore server.p12 -storepass ballerina \
    -rfc -file server-public.crt
  ```
  Then copy `server-public.crt` into `rental_client/`.

## Known limitations

- **In-memory storage only** (as the assignment specifies) — all data
  (properties, users, bookings) is lost when the server restarts. No
  database or file persistence.
- **No concurrency locking on the in-memory maps.** Ballerina flags this
  with `isolated`-method HINTs during compilation. We deliberately did not
  add locking: Ballerina's `lock` only provides real protection if *every*
  function touching a given shared map (`properties`, `users`,
  `pendingBookings`, `confirmedBookings`) uses it consistently — locking
  some functions while leaving others unlocked gives no actual safety
  benefit, since an unlocked function can still read/write the same data
  at the same instant. Retrofitting this correctly across all 8 RPCs plus
  the `authenticate`/`cleanupExpiredBookings` helpers this close to the
  deadline carried real risk of introducing new bugs for a benefit that's
  unlikely to matter in practice for how this system is tested and
  demoed (one or two people manually driving the client, not many
  concurrent users hitting the exact same data in the same instant). This
  was a deliberate, considered trade-off, not an oversight — we can
  explain the exact failure scenario (two simultaneous writes to the same
  record silently corrupting each other) and why a full, consistent fix
  was out of scope given the remaining time.
